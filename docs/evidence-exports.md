# Evidence, audit, retention, and client exports

## Implemented path

An authenticated `EVENT_INGESTOR` uploads up to 64 MiB of raw bytes to
`POST /v1/evidence`. The API derives the tenant from the signed token, writes
the bytes to a private object root using a generated key, checks SHA-256, and
appends tenant-scoped metadata and an audit event. A normalized event may use
`rawEventReference: "evidence:<uuid>"`; ingestion verifies that the evidence
ID is visible in the same RLS transaction and creates an immutable link.
Existing external `rawEventReference` values remain accepted for compatibility
but are **not** MARID-stored or verified evidence.

`IObjectStore` isolates object operations from the domain. The included
`FileObjectStore` writes a temporary file, flushes it, and atomically promotes
it on a private persistent volume. Keys are generated by MARID and never
accepted from an HTTP request. No bucket or filesystem path is returned in
API responses. A production deployment must provide a private durable volume
at `MARID_OBJECT_ROOT`; S3-compatible, Azure Blob, R2, or client storage
adapters can implement the same streaming contract. The current adapter has
not been validated for distributed multi-node use.

Client auditors or incident managers request an explicit UTC interval with
`POST /v1/exports` and an idempotency key. The separate `marid_worker` database
identity claims only queue metadata globally. It then sets `app.tenant_id` in
every transaction that reads source rows. The worker streams ordered NDJSON in
calendar-month partitions, writes a structured `report.json` and a basic readable
`report.md`, and finalizes a
`manifest.json` with export/tenant IDs, interval, generation timestamp,
versions, file names, row counts, sizes, and SHA-256 digests. Partitions already
committed to the database are verified and reused after a retry. An identical
idempotency key returns the same job; a different interval conflicts. The
worker renews its lease and retries a failed job up to five times. Monthly
schedule defaults to day 1 UTC and can be changed per tenant. The API returns
job status immediately; downloads are separate authorized requests.
Download every artifact into one directory using its returned file name,
then run:

```text
python scripts/verify-export.py manifest.json <directory> --expected-manifest-sha256 <trusted-hash>
```

The expected hash is shown in the
job status response. For stronger origin proof it must come from a separate
trusted channel or a future KMS signature.

The basic reports contain an executive heading and activity counts. Detailed
security records are in NDJSON. Evidence metadata includes SHA-256 and an
opaque evidence ID; raw bytes can be retrieved separately through the
authorized evidence download route. The current package does not embed raw
objects, render PDF/HTML, produce Parquet, or send archives to customer buckets.
`IManifestSigner` is the integration point for an external KMS/HSM signer.
No signer is configured now. SHA-256 checks detect corruption, but an actor
controlling both database and object storage could replace an unsigned package.
External signing and independent checkpoint retention are production gates.

## Accountability and tenant boundary

The existing `audit_events` table now records explicit actor classes, session,
reason, ticket, target, outcome, and severity fields. Signed Keycloak claim
`marid_actor_class=NOCTURNE_ENGINEER` identifies engineer tokens. A tenant
role grant and `operator.session` scope are still required. Engineers must
start a session with a reason and ticket. Every `/v1` request made with that
claim requires the session header and appends a tenant audit event. Break-glass
sessions produce high-priority records. An explicit action route records work
outside MARID's HTTP API. Production Keycloak provisioning must ensure only
Nocturne identities can receive this signed claim and must enforce MFA/JIT;
the current repository does not provision that realm.

Signed `marid_actor_class=MARID_AGENT` service tokens classify agent activity.
The record-only execution endpoint connects an event-backed proposal to its
approval and outcome, verification, and rollback notes. It is **not** a tool
executor or an authorization to perform actions. No private model reasoning
is stored. Incidents have append-only activity and event links so exports can
show investigation, status, and remediation notes alongside proposals and
execution records. Historical incidents receive an initial migration snapshot;
their earlier state changes cannot be reconstructed retroactively.

All tenant-owned tables use forced RLS and composite tenant foreign keys where
records link. The application role cannot UPDATE/DELETE evidence or audit rows,
own protected tables, bypass RLS, or claim cross-tenant export jobs. A narrow
security-definer lock function checks the session tenant explicitly before a
legal hold is inserted. A separate worker role can mark retention tombstones,
but its evidence queries still set tenant context. The worker's global queue
claim and tenant enumeration never return another tenant's evidence to an API
client. Tests exercise guessed IDs, cross-tenant links, holds, exports, and
artifact retrieval.

## Retention and delivery

New tenants receive separate default days for telemetry (365), raw evidence
(365), audit (2555), incidents (2555), and exports (365). A tenant incident
manager with `retention.admin` can change these values and apply or release a
legal hold. The worker currently **enforces RAW retention only** for the `RAW`
class. It excludes active legal holds and pending export intervals, appends a
retention audit event, marks a tombstone, deletes the object, and records the
storage deletion. If object deletion fails, the tombstone remains and the next
run retries. `EXTENDED` objects and the other policy categories are retained
until their deletion workflows are implemented. This conservative behavior
prevents unaudited deletion, but can exceed configured retention periods.

API retrieval is the implemented delivery channel. Each successful artifact
or manifest retrieval creates a tenant delivery receipt and audit record.
Customer-controlled bucket/SFTP delivery, secret references for those targets,
notifications, and delivery verification are not implemented. Credentials must
never be placed in tenant tables or application logs.

## Threat model and operations

The controls address guessed IDs, request-body tenant spoofing, path traversal,
cross-tenant joins, mutable evidence metadata, altered object bytes, and job
retries. They rely on the trusted API/worker binaries, authenticated IdP,
PostgreSQL role separation, a private object root with durable backup, and
correct host clock. A compromised migration owner, host administrator, IdP,
or both database and object storage remains outside the current integrity
boundary. The development database owner is a superuser; production should
use a restricted migration identity and separately managed worker credential.

Back up PostgreSQL and the object root as one recovery set. Restore both,
validate every object against its metadata digest, rerun an idempotent export,
and retain old manifests independently. Test interrupted uploads, lease expiry,
corrupted objects, legal holds, and storage loss before customer use. The
current disposable tests cover DB restore and local object hashing; they do
not establish production backup retention, KMS signing, multi-node locking,
performance at terabyte scale, or full disaster recovery.
